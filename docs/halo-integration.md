# 기회 발굴·라이브러리 통합 운영 가이드

GEO_master의 측정·SQLite·인증·LLM·키 관리 체계를 유지하면서 haloX 계획의 기회 후보 관리, 작성 페르소나, 지식 자료 기능을 구현했다. 별도 haloX 서버, JSON 상태 저장소, 목업 Provider, 인증·결제 코드는 가져오지 않았다.

## 활성화와 복구

1. 기존 워크스페이스를 내보내고 서버 환경에 `GEO_ENABLE_HALOX=1`을 설정한다.
2. 서버를 다시 시작한다. SQLite는 최초 접근 시 추가 마이그레이션 32·33을 순서대로 적용한다.
3. `/opportunities`, `/library`, `/studio`에서 기능을 확인한다.
4. 문제가 있으면 `GEO_ENABLE_HALOX=0`으로 바꾸고 다시 시작한다. 메뉴·신규 API·새 작성 문맥 선택은 닫히며 추가 데이터와 기존 생성 이력은 보존된다. 테이블을 삭제하거나 DB 버전을 되돌릴 필요가 없다.

기본값은 비활성이다. 운영 배포와 기능 활성화 설정, API 키는 이번 구현에서 변경하지 않았다. 브라우저 검증에는 별도 임시 DB를 사용했다. 신규 기능의 접근 정책은 기존 스튜디오·사실 메모와 같다. 계정들이 프로젝트와 활성 프로젝트 설정을 공유하는 기존 제약도 유지된다.

## 사용자 흐름

1. `/monitoring`에서 질문을 등록하고 기존 측정 기능으로 실행한다.
2. `/opportunities`의 **후보 갱신**을 누른다. 외부 호출 없이 저장된 질문별 최신 완료 실행으로 후보를 계산한다.
3. 원문·모델·측정 시각·표본·인용을 확인한 뒤 보류하거나 채택한다. 등록 질문을 재사용하고, 신규 질문이면 선택한 세트에 추가한다. 채택은 질문 유형의 전략 과제를 생성한다.
4. `/library`에서 브랜드 자료와 페르소나를 작성한다. 출처 URL은 기록만 하며 자동 수집하지 않는다. 수치·가격·인증은 기존 `/facts`에서 별도로 검증한다.
5. **이 기회로 콘텐츠 작성**으로 이동하고 페르소나 1개, 자료 최대 5개를 선택한다. 참고 문맥의 직렬화된 전체 크기는 30,000자 이내다. 기존 네 Provider 중 하나를 이용한다.
6. 생성 당시 내용·수정 시각·사실 메모를 이력과 revision에 보존한다. 문맥을 사용한 새 결과는 `draft`로 저장되며 기존 콘텐츠 이력에서 `review`, `approved`로 진행한다. AI 응답 판정용 검수함과 별개다.
7. 본문을 수동 반영한 뒤 기회에 URL·반영일을 기록한다. 실제 웹사이트를 변경하는 작업은 아니다. WordPress 기능의 지원 범위는 그대로다.
8. 같은 질문을 재측정하고 이후 완료 실행을 기회에 연결한다. 실행 조건이 같을 때 언급률·인용률 변화(%p)를 표시한다. 조건 차이와 미측정은 별도 안내하고 인과관계를 단정하지 않는다.

## 판정·일관성 규칙

- 지원 Provider의 정상 답변만 언급 분모에 포함한다. 실패·거절·미측정은 0점으로 계산하지 않는다.
- 인용 지원이 확인된 정상 답변의 `cited` 항목만 인용 근거로 사용한다. 본문에 단순히 포함된 URL은 제외한다.
- 질문 정규화(NFKC, 공백, 대소문자)와 프로젝트·유형 유일 제약으로 중복 후보를 막는다. 후보는 발견 시점의 기록이며, 이후 갱신에서 안 나타났다고 자동 삭제하지 않는다.
- 채택·보류한 후보의 기준 근거는 고정한다. 반복 채택은 동일 연결을 반환한다. 원본 삭제 시 연결 해제를 표시하고 보존된 근거를 다른 실행으로 바꾸지 않는다.
- 수정·삭제는 `expectedUpdatedAt`으로 동시 변경을 감지한다. 브라우저는 `x-geo-project-id`를 보내며 서버가 본문 파싱 후 활성 프로젝트와 다시 비교한다.
- 스튜디오는 요청의 `projectId`와 문맥을 외부 호출 전에 확정한다. 호출 중 프로젝트가 바뀌어도 시작한 프로젝트에 저장한다.
- `clientRequestId`와 문맥 버전 해시를 SQLite에 먼저 기록해 중복 호출을 막는다. 외부 호출 중 쓰기 트랜잭션을 유지하지 않는다. 결과·revision·기회 연결·완료 상태는 외부 호출 후 한 트랜잭션으로 저장한다.
- 생성 중 워크스페이스를 교체 복원하거나 시작 프로젝트를 삭제하면 실행 토큰이 무효화된다. 늦게 도착한 응답은 복원된 프로젝트에 저장하지 않는다. 요청 ID를 다시 사용하더라도 이전 실행이 새 실행 상태를 변경할 수 없다.
- 후속 실행도 처음 연결한 원문·분모를 보존한다. 일부 응답 또는 실행이 삭제되면 연결 해제를 표시하고 전후 비교를 중단한다. 같은 실행을 다시 저장해도 스냅샷은 바뀌지 않는다.
- 프로세스 중단으로 실행 상태가 남으면 자동으로 재호출하지 않는다. 이력을 확인한 뒤 **새 요청으로 다시 준비**로 명시적으로 재시도한다.
- 자료·페르소나 삭제 후에도 과거 생성 문맥이 남는다. 사실 메모와 충돌하는 참고 문맥은 사실 근거로 인정하지 않고 기존 생성 결과 검사를 적용한다. 이는 AI 결과의 사실성을 보증하는 기능은 아니다.

## 데이터와 API

마이그레이션 32는 다음 6개 테이블을 추가한다.

| 테이블 | 역할 |
|---|---|
| `knowledge_documents`, `writing_profiles` | 프로젝트에 귀속된 자료·문체와 버전 시각 |
| `opportunities` | 후보·상태·근거·질문·전략·기준/후속 실행·반영 기록 |
| `opportunity_decisions` | 판단 이력 |
| `opportunity_contents` | 생성 콘텐츠 연결 |
| `studio_requests` | 동시 중복 생성 방지 |

마이그레이션 33은 `studio_requests.execution_token`과 `opportunities.followup_evidence`를 추가한다. 기존 테이블·콘텐츠를 재작성하거나 삭제하지 않는다.

API는 기존 JSON 오류 형식을 따른다.

| 경로 | 동작 |
|---|---|
| `/api/opportunities` | GET 목록·질문 세트·완료 실행 / POST 직접 입력 후보 |
| `/api/opportunities/refresh` | POST 저장 측정 기반 후보 갱신 |
| `/api/opportunities/[id]` | GET 상세 / PATCH 상태·메모·반영·후속 실행 / DELETE |
| `/api/opportunities/[id]/adopt` | POST 채택 (`expectedUpdatedAt`, 선택적 `questionSetId`) |
| `/api/knowledge-documents`, `/api/writing-profiles` | GET 목록 / POST 생성 |
| 각 자료의 `/[id]` | GET 상세 / PATCH `{data, expectedUpdatedAt}` / DELETE `{expectedUpdatedAt}` |
| `/api/studio` | 기존 입력과 선택적 `projectId`, `opportunityId`, `writingProfileId`, `knowledgeDocumentIds` |

워크스페이스 내보내기는 schema v3다. v1·v2 가져오기를 유지하며 v3 병합 시 신규 관계와 콘텐츠·revision의 생성 문맥 참조 ID를 재매핑한다. 삭제된 원본 참조는 `null`로 바꾸고 당시 텍스트·버전은 보존한다. 잘못된 프로젝트 관계는 전체 가져오기를 롤백한다. 실행 잠금(`studio_requests`)과 비밀 키는 백업에서 제외한다.

생성 문맥의 전체 구조에 맞는 데이터만 관계를 재매핑한다. 예전 수동 콘텐츠에 같은 이름의 임의 JSON 값이 있어도 보존한다. 과거 이력을 다시 작성 화면에 불러오면 삭제된 선택 ID는 제외하며, 저장된 과거 문맥은 그대로 남는다.

## 검증과 범위

핵심 통합 테스트는 `tests/halo.integration.test.ts`에 있다. 후보 판정, 채택 멱등성, 프로젝트 전환·동시 수정, 자료 변경·삭제 중 생성, 실패·재시도, 미확인 수치, 원본 삭제, 조건 비교, v1/v2/v3 복원, ID 재매핑, 기능 플래그를 검증한다.

실행 결과·브라우저 증거는 `output/halo-integration/2026-10-25/` 및 `output/halo-integration/2026-10-25-completion/`에 기록한다. 브라우저는 별도 임시 DB의 명시적 QA 측정 자료를 사용했고 실제 유료 Provider 호출은 하지 않았다. 기존 측정·예약·revision·리포트·WordPress는 전체 회귀 테스트로 확인한다.

파일 파싱, 크롤링, 벡터 검색, Google GSC/GA4 자동 수집, 새 질문·검색량 생성, 별도 점수 공식, 고객별 SaaS 격리는 이번 범위에 포함하지 않는다.
