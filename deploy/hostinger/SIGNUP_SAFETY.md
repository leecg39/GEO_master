# 가입 안전장치와 공개 운영 전 확인

PR #28 수정 검토 · 2026-10-10 KST. 운영 서버를 변경하거나 운영 데이터로 시험하지 않았습니다.

검증: `npm test` 99개 파일·798개 테스트 통과(기존 783개 + 추가 15개), `npm run typecheck`, `npm run lint`, `npm run build` 통과. 가입·로그인·승인 라우트와 프록시를 임시 SQLite DB로 검증했습니다. 기존 PR의 실제 HTTP 28건·Chrome E2E 16건은 이번 작업에서 재실행하지 않았습니다.

## 관리자 없는 가입 방지

가입 방식은 `signupMode()`에서 일관되게 결정합니다. 로그인 가능한 환경 변수 관리자 또는 관리자 역할을 가진 HTTP 인증 계정이 없으면 `approval`과 `auto` 모두 `closed`가 됩니다. 페이지를 숨기는 것에 더해 가입 서비스가 직접 POST를 403으로 거절하므로 우회 가입·승인 대기 계정 생성도 막힙니다. 이 검사는 요청 시 적용되어 빌드 시점 환경 변수를 고정하지 않습니다.

- `.env` 관리자: 유효한 아이디와 8자 이상·72바이트 이하 평문 또는 유효한 bcrypt 형식. 잘못된 bcrypt 설정은 평문으로 해석하지 않습니다.
- HTTP 계정: 로그인 코드가 파싱한 bcrypt 계정과 관리자 역할이 함께 필요합니다. 역할만 있거나 일반 운영 계정만 있어서는 부족합니다.
- 게스트 역할 우선순위와 이메일 아이디 정규화, `.env` 관리자의 HTTP 계정 가림 규칙도 적용합니다.
- 명시적 `closed`·알 수 없는 모드는 계속 닫힙니다. 기존 회원 로그인과 세션은 가입 중단과 독립적입니다.
- 코드에서 비밀번호·해시·토큰·환경 변수 값을 새로 로깅하지 않습니다.

## 현재 접근 범위와 위험

| 범위 | 코드상 확인 결과 | 공개 운영 전 위험 / 필요한 조치 |
| --- | --- | --- |
| 프로젝트 조회·생성·수정·삭제·전환 | `account-policy.ts`는 customer의 `/api/projects`를 허용. `projects.ts`는 계정 소유권 조건 없이 조회·변경. 활성 프로젝트는 `settings.id=1`의 공용 값 | **고위험**: 다른 고객 자료 조회·수정 및 전체 사용자 작업 대상 변경. 테넌트별 프로젝트 소유권과 사용자별 활성 프로젝트 필요 |
| GEO 측정·질문·콘텐츠·진단·보고서 | customer 경로 제한 대상이 아님. `requireActiveProject()`는 공용 활성 프로젝트와 일치하는지만 검사 | **고위험**: 프로젝트 범위 검사는 고객 격리가 아님. 테넌트 키와 모든 읽기·쓰기·내보내기의 서버 소유권 검사 필요 |
| 보고서 공유 링크 | `/api/report-shares`는 게스트만 제한. `report-shares.ts`는 공용 활성 프로젝트의 완료 측정이면 생성·목록·폐기 허용. `/r/<token>`은 공개 조회 | **고위험**: 회원이 공유 자료를 외부에 공개 가능. 고객 소유권과 외부 공유 권한·승인 정책 필요 |
| 측정·자동화 등 실행 | customer가 관련 API 경로에 접근 가능하며 설정 화면 차단은 실행 API를 차단하지 않음 | **고위험**: 공용 제공자 설정을 사용하는 실행의 비용·작업 충돌 가능. 고객별 실행 권한·사용량 한도·작업 격리 검증 필요 |
| 설정·백업/복원·회원 관리 | `/settings`, `/workspace`와 대응 API는 customer 차단. `/admin`과 API는 admin만 허용 | 역할별 경계는 존재. 이것만으로 업무 데이터는 격리되지 않음 |
| SEMForge 구독·결제 | `semforge-subscription.ts`는 `account_id`로 구독·결제 분리, 업무 API는 구독 검사 | 결제 권한 분리는 업무 데이터 소유권 분리와 별개. 유료 회원끼리의 프로젝트·업무 자료 격리 검증 필요 |

테스트는 두 가입 계정이 같은 프로젝트를 보고 한 계정의 프로젝트 전환이 다른 계정에도 반영되는 현재 동작을 재현합니다. 이는 알려진 위험의 기록이며 안전한 다중 고객 운영을 증명하는 테스트가 아닙니다. 격리를 구현할 때 이 테스트를 상호 접근 거절 기대값으로 교체해야 합니다.

## 운영 선택지

1. **가입 중단**: `closed`로 유지하면서 고객 격리를 구현합니다. 외부 고객 공개 모집 전 기본 권장안입니다.
2. **신뢰하는 한 조직 내부 사용**: 유효한 관리자와 `approval`을 사용하고 모든 승인자가 공유·수정 범위를 이해하도록 합니다. 외부 고객 격리 대안은 아닙니다.
3. **고객별 별도 인스턴스**: DB·볼륨·비밀·도메인을 분리해서 운영하거나, 테넌트 모델과 서버 접근 검사를 구현한 뒤 다중 고객 서비스를 개방합니다.

## 배포 영향 확인 순서

1. PR 수정은 코드와 테스트만 반영합니다. 운영 환경 변수·비밀·DB·실행 컨테이너는 변경하지 않습니다.
2. 운영 담당자는 기존 관리자 인증 방식과 게스트 중복 여부를 값 노출 없이 확인합니다. `env`, 완전히 보간된 `docker compose config`, 인증 헤더를 공유 로그에 출력하지 않습니다.
3. 배포 후 관리자 미설정이면 가입이 닫히는 것이 정상입니다. 기존 계정 로그인에는 영향을 주지 않습니다. 잘못된 bcrypt 설정을 사용하던 계정은 올바른 설정으로 복구해야 합니다.
4. 관리자 설정이 유효한 별도 검증 환경에서 가입 → 대기 로그인 차단 → 관리자 승인 → 회원 로그인, `closed`에서 새 가입 거절과 기존 로그인 유지, 비관리자의 관리 API 차단을 확인합니다.
5. 운영 비밀 변경은 별도 영향 검토 후 수행합니다. 관리자 비밀번호 변경은 기존 관리자 세션을 무효화할 수 있습니다. 가입 모드 변경 자체는 기존 회원 세션을 취소하지 않습니다.
